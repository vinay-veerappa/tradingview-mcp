- [BLOCKER] src/gateway/http.js: `handleStream` — the `for await` loop over `subscribe()` has no timeout or backpressure handling. If the subscriber's `shouldStop` never fires (e.g., the client disconnects but the `close` event is not emitted because the socket is half-open, or the SSE response is never flushed), the loop runs forever, leaking the poll timer. The `req.on('close')` and `res.on('close')` handlers set `disconnected.stop = true`, but there is no `setTimeout` fallback to force termination. A client that opens `/stream/quote` and then goes silent (no TCP FIN, no RST) will leave the gateway's `subscribe()` loop running indefinitely, holding the CDP connection and the event loop. Concrete failure: `curl -N http://127.0.0.1:9223/stream/quote` then kill the process with SIGKILL — the server-side `close` event may never fire, and the poll loop persists.
- [MAJOR] src/gateway/http.js: `handleRequest` — the 405 check happens AFTER the 404 check, but the 404 check uses `ROUTES.some((r) => r.path === url.pathname)` which only matches exact paths. A POST to `/stream/quote` (a valid stream path) falls through to the 404 branch because `pathMatch` is only checked for `/stream/<kind>` at the top, and the 405 check is after the 404 check. So `POST /stream/quote` returns 404, not 405, violating the stated invariant "any non-GET → 405". Concrete failure: `curl -X POST http://127.0.0.1:9223/stream/quote` returns `{"success":false,"error":{"code":"http_not_found",...}}` instead of `http_method_not_allowed`.
- [MAJOR] src/gateway/http.js: `handleStream` — the `catch {}` block swallows ALL errors, including the case where `subscribe()` itself throws (e.g., a CDP connection error that is not a clean `connection-lost` event). The comment says "client gone mid-write or subscriber error — nothing to do", but a subscriber error that is NOT a disconnect (e.g., an internal bug in `subscribe()`) is silently swallowed, and the client gets a truncated SSE stream with no error event. The error envelope contract is broken: the client never sees `{success:false, error:{code, retryable}}` for a genuine upstream failure on a stream route. Concrete failure: if `subscribe()` throws `new Error('internal bug')`, the client receives only the `:ok` prelude and then the connection closes with no error indication.
- [MAJOR] src/core/context.js: `withChartContext` — the abort race has a subtle bug: when `signal` is provided and the op wins the race, the `abortP` promise is never settled (the `abort` listener is never removed). This leaks a listener on the signal for the lifetime of the signal. If the caller reuses the same `AbortController` for many `withChartContext` calls (e.g., a long-lived MCP session), each call adds a listener that is never removed, eventually exhausting memory or causing the abort handler to fire on a stale promise. Concrete failure: 10,000 sequential `withChartContext` calls with the same signal → 10,000 leaked listeners; when the signal finally aborts, all 10,000 `rej(abortError)` calls fire, but only the last one's promise is still pending — the rest are no-ops, but the listener leak is real.
- [MAJOR] src/core/context.js: `withChartContext` — the pre-aborted check `if (signal?.aborted) throw abortError;` is inside the `run` closure, which is chained on `_lock.then(...)`. If the lock is held by a long-running op, a pre-aborted signal does NOT reject the caller immediately — it waits for the lock to be released. The test `'P2-18: pre-aborted signal throws before touching the chart'` passes because the lock is free, but in a real scenario where another op holds the lock, the caller's abort is delayed until the lock frees. The comment says "pre-aborted signals never touch the chart" — that's true, but the caller is not rejected promptly. Concrete failure: op A holds the lock for 10s; caller B calls `withChartContext(..., {signal: preAbortedSignal})`; B's promise does not reject until A finishes, violating the cancellation contract.
- [MINOR] src/gateway/http.js: `handleRequest` — the `route.handler` is called with `(req, url, _deps)`, but the `/capabilities` route handler is defined as `handler: () => ({...})` — it ignores `_deps`, which is fine, but the `/state` route calls `getState({ _deps })` — this matches the core signature (getState takes `{_deps}`), but the `/panes` route calls `paneScan(_deps)` — this matches the core signature (paneScan takes deps directly). The signature drift is correct here, but the inconsistency is a maintenance hazard: a future reader may "fix" one to match the other and break the call. Not a bug, but a code smell.
- [MINOR] src/gateway/http.js: `handleStream` — the `interval` query param is parsed with `Number(url.searchParams.get('interval'))` but never validated. If a client sends `interval=abc`, `Number('abc')` is `NaN`, and `subscribe(kind, { interval: NaN, ... })` may behave unpredictably (e.g., `setInterval` with `NaN` fires immediately or never). Concrete failure: `curl -N "http://127.0.0.1:9223/stream/quote?interval=abc"` → `NaN` interval, potentially a tight loop or no polling at all.
- [MINOR] src/cli/commands/gateway.js: the `handler` never resolves (`await new Promise(() => {})`), which is intentional, but the `shutdown` function calls `close()` then `process.exit(0)`. If `close()` throws (e.g., a socket destroy error), `process.exit(0)` is never reached, and the process hangs. The `close()` in `startGateway` wraps `server.close()` in try/catch, but `stopAll()` calls `c.destroy()` without a try/catch per connection (only a try/catch around the whole loop, which would abort the loop on first error). Concrete failure: if one connection's `destroy()` throws, the loop stops, remaining connections stay open, `server.close()` never completes, and the process hangs on Ctrl-C.
- [MINOR] tests/gateway.test.js: the `getSse` helper uses `fetch` with an `AbortController`, but the abort fires after `ms` milliseconds. The test `'SSE stream serves event-stream and emits connection events offline'` uses `ms=600`, but the offline `subscribe()` emits `connection-lost` immediately, so the test passes. However, the test does NOT verify that the poll loop actually terminates on abort — it only checks the body content. The P2-18 cancellation claim ("no orphaned poll loops") is not tested. Concrete missing case: after abort, assert that the gateway's `subscribe()` loop has stopped (e.g., by checking that no further events are emitted or that the server's connection count drops to zero).
- [MINOR] src/core/health.js: the `repoRoot` computation `dirname(dirname(dirname(fileURLToPath(import.meta.url))))` assumes the file is at `src/core/health.js` (3 levels deep from repo root). If the file is ever moved (e.g., to `src/health.js`), the anchor breaks silently and `git` commands run from the wrong directory again. The comment says "Same pattern as update.js REPO_ROOT" — but the pattern is fragile and should be a single `find-up` or a constant. Not a bug today, but a regression risk.
- [MINOR] src/core/snapshot.js: `sessionSnapshot` passes `signal: _deps?.signal` to `withChartContext`, but `_deps` is the second parameter of `sessionSnapshot(opts = {}, _deps = null)`. The MCP tool calls `sessionSnapshot(args, { signal: extra?.signal })` — this is correct. But the gateway route calls `sessionSnapshot(opts, _deps)` where `_deps` is the gateway's injected deps — if the gateway's `_deps` does NOT include a `signal` property (which it doesn't in `startGateway`), the signal is `undefined`, and cancellation is silently disabled for HTTP calls. This is fine for the first slice (HTTP has no cancellation), but the comment in `src/tools/snapshot.js` says "MCP request cancellation" — the gateway path is not covered, which is acceptable but should be documented.
