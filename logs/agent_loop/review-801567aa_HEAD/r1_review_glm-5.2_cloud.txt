- [BLOCKER] context.js: `withChartContext` pre-abort check bypasses the serialization lock, so a pre-aborted call never enters the `new Promise` executor and never calls `resolve`. The caller's `await` rejects correctly, but the queue's internal `next()` chain is never advanced for that slot — the call was never queued, so there is no slot to advance. This is actually correct for the *caller*, but the defect is subtler: the pre-abort check returns *before* the `new Promise` is even constructed, so the function returns `Promise.reject(...)` synchronously. A pre-aborted call made while the lock is held rejects immediately (good), but a pre-aborted call made while the lock is *free* also rejects immediately without ever acquiring or releasing the lock (also fine). The real problem: the pre-abort path skips the lock entirely, but the lock acquisition is what guarantees serialization. If two calls arrive simultaneously — call A (no signal, slow op) and call B (pre-aborted signal) — call B rejects instantly without waiting, which is the intended behavior. **However**, the pre-abort check is outside the `new Promise`, so it runs before any lock interaction. This means a pre-aborted call can observe and reject against a chart state that is mid-transaction by another call, but since it never touches the chart, this is safe. No defect here on re-analysis — downgrade to informational.

- [MAJOR] context.js: `opP.catch(() => {})` in the `finally` block attaches the catch handler *after* `await Promise.race([opP, abortP])` has already settled. If `opP` rejects *before* the `finally` runs (i.e., the op synchronously throws or rejects before abort wins), the rejection has already been observed by `Promise.race` and is handled. But if `opP` rejects *after* `finally` runs (the "late reject" case the comment describes), the `opP.catch(() => {})` is attached in the `finally`, which runs before `opP` settles — so the catch IS attached in time. **The actual defect**: `opP.catch(() => {})` creates a *new* promise that is never awaited. If `opP` rejects after the `finally` block completes but the `.catch()` handler itself throws (it won't, since it's `() => {}`), this is fine. But the real issue: the `.catch()` is attached synchronously in the `finally`, so it catches the late rejection. This is correct. No defect — downgrade.

- [MAJOR] http.js: `interval` validation rejects `interval < 50` but the existing test was changed from `?interval=40` to `?interval=100`. The test was updated to pass the new threshold, but the threshold of 50ms is undocumented in any ADR and the original test used 40ms, suggesting the production default or expected minimum was lower. If any existing client or configuration uses `interval=40` (or any value 1–49), this change is a **silent breaking regression** — previously it worked (NaN-safe fallback for falsy, `setTimeout` with small positive values), now it returns 400. The comment says "NaN falls back safely (falsy)" but the old code was `url.searchParams.get('interval') ? Number(...) : undefined` — a value of `'0'` is truthy as a string, so `Number('0')` = 0, and `setTimeout(..., 0)` is valid. Now `interval=0` returns 400. **Concrete failing case**: `GET /stream/quote?interval=0` previously streamed with 0ms delay (effectively no polling interval / as-fast-as-possible), now returns 400 `http_bad_request`.

- [MAJOR] http.js: `knownPath` for non-GET requests includes `Boolean(pathMatch)`, so `POST /stream/quote` returns 405 (correct). But `DELETE /stream/unknownkind` — `pathMatch` matches `/^\/stream\/([a-z]+)$/` so `pathMatch[1]` = `'unknownkind'`, `knownPath` = true, returns 405. Then for GET, `handleStream` is called and returns 404 for unknown kind. **But for non-GET**, `DELETE /stream/unknownkind` returns 405 instead of 404 — the method check happens before the kind validation. This is arguably correct (method takes precedence), but the 405 response includes `Allow: GET` even though GET would 404. A client seeing 405 + `Allow: GET` would retry with GET and get 404. This is a minor semantic issue, not a blocker.

- [MAJOR] http.js: The `catch (err)` block in `handleStream` writes an SSE error event but does NOT set `disconnected.stop = true` or `break` out of the loop. The `for await` loop is already exiting because the iterator threw, so the loop body won't re-enter. But if `subscribe` is a generator that catches internally and continues yielding (unlikely but possible depending on implementation), the error event would be written and the loop would continue. More importantly: after writing the error event, `res.end()` is called in the `try { res.end() }` block. If the client is still connected, they receive the error event then EOF. This is correct behavior. No defect.

- [MINOR] context.js: The pre-abort check creates `abortError` with `new Error(...)` and sets `.name = 'AbortError'` but does not set `.code` or make it an actual `DOMException`/`AbortError` instance. Code that checks `err instanceof AbortError` or `err.code === 'ABORT_ERR'` (common in Node.js abort handling) will not match. The test only checks `/aborted by caller/` regex, so it passes, but downstream consumers using standard abort detection patterns will fail to recognize this as an abort.

- [MINOR] http.js: `Allow: knownPath ? 'GET' : undefined` — when `knownPath` is false, `Allow` is set to `undefined`, which `writeHead` will include as a header with value `undefined`. Node.js `res.writeHead` with an `undefined` header value behavior is version-dependent; in some versions it writes the literal string "undefined", in others it omits it. Should be `Allow: knownPath ? 'GET' : undefined` → better to conditionally include the header only when `knownPath`.

- [MINOR] tests/context.test.js: The listener leak test uses `ctl.signal._events` which is an internal Node.js property not part of the public API. On Node 20+, `AbortSignal` may not expose `_events` directly (it uses internal native backing). The test's fallback chain `?? before ?? 0` where `before = undefined` means if `_events` is undefined, the assertion becomes `assert.ok(0 === 0)` which always passes — **the test cannot actually detect a listener leak**. The test is a no-op on modern Node versions.

- [MINOR] tests/gateway.test.js: The interval validation test only checks `?interval=-5` and `?interval=abc` but does not test `?interval=0`, `?interval=49`, `?interval=50` (boundary), `?interval=50.5` (fractional), or `?interval=` (empty string, which `Number('')` = 0 → 400). The boundary at 50 is not tested from either side.
